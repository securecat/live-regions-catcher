What this extension shows

Live Regions Catcher displays, chronologically in the side panel, the notifications that a web page attempts to convey to browsers and assistive technologies. Each entry is called a catch.

It is not a reproduction or recording of what a screen reader actually speaks. What you see is the page's notification intent, as observable from the DOM and Web APIs. Whether and how a real screen reader announces it varies by browser, screen reader, and their settings. The caught content itself is always kept verbatim — never translated or rewritten.

What gets caught

Explicit live regions

Elements with aria-live="polite" or aria-live="assertive", including liveness inherited from ancestors. polite is treated as normal priority, assertive as high priority.

Implicit live regions

Roles with implicit liveness are monitored even without an aria-live attribute:

RoleEffective aria-liveEffective aria-atomic
statuspolitetrue
logpolitedefault
alertassertivetrue

role="timer" and role="marquee" are implicitly off and are not caught unless explicitly made live.

Effective values

For each catch, the extension resolves the effective values of aria-live, aria-atomic, and aria-relevant — taking the element's own attributes, inherited ancestor values (including across shadow boundaries), and role defaults into account. Explicit values win over role defaults. Both the explicit attribute values and the resolved effective values are shown in each catch's details.

ariaNotify()

In browsers that implement it, imperative notifications via document.ariaNotify() and element.ariaNotify() are caught, with their priority and call target. Calls made before the observer is injected cannot be caught.

Region insertion and empty notifications

How a live region is created and updated changes how its catches are handled. Three patterns are worth knowing.

1. A region inserted together with its content

const status = document.createElement('div');
status.setAttribute('role', 'status');
status.textContent = 'Saved!'; // content is already inside
document.body.append(status);  // …when the region enters the DOM

Inserting a region is not a change within a region, so whether assistive technologies announce it varies across environments. Frameworks that re-render loading placeholders often produce bursts of this pattern. It is caught with a note.

2. Inserted empty, updated later — the recommended practice

<div role="status" id="save-status"></div>

// later, when the notification should happen:
document.getElementById('save-status').textContent = 'Saved!';

An empty live region is prepared first, and content is set when a notification is needed. The empty insertion itself is not caught; the update that fills in content is caught normally.

3. Empty notifications

document.getElementById('save-status').textContent = '';

An update happened, but the announceable content came out empty — for example when a message is cleared, or when the changed content is entirely hidden from the accessibility tree. It is caught and marked as empty.

Modal dialogs

While a visible aria-modal="true" dialog (role="dialog" or role="alertdialog") is open, browsers and screen readers disagree on whether live regions outside it are announced. The extension marks each catch as inside or outside "the modal as judged by this extension" (a heuristic), and lets you choose to catch, ignore, or annotate outside notifications.

What cannot be caught

  • Changes that happened before observation started on page load, and ariaNotify() calls made before the observer was injected
  • Changes inside closed shadow DOM
  • Changes to an input element's current value inside a live region — assignments to the value property and user typing do not appear as DOM mutations, so they cannot be observed (changes to the value attribute via setAttribute() are caught)
  • The actual spoken output of a screen reader (each screen reader phrases things in its own way, which this extension cannot know; it captures the live region's value before it reaches the screen reader)

この拡張が表示するもの

ライブリージョン・キャッチャーは、Webページがブラウザや支援技術へ伝えようとした通知を、サイドパネルに時系列で表示します。1件1件の記録をキャッチと呼びます。

スクリーンリーダーが実際に発話した内容の再現や記録ではありません。表示されるのは、DOMとWeb APIから観測できる「ページ側の通知の意図」です。実際に通知されるかどうか・どう読まれるかは、ブラウザ・スクリーンリーダー・その設定の組み合わせによって異なります。キャッチした内容そのものは常に原文のまま保持し、翻訳や書き換えは行いません。

何をキャッチするか

明示的なライブリージョン

aria-live="polite" または aria-live="assertive" が指定された要素です（祖先からの継承も含みます）。polite は通常優先度、assertive は高優先度として扱います。

暗黙のライブリージョン

次のロールは、aria-live 属性がなくても監視対象です：

ロール実効aria-live実効aria-atomic
statuspolitetrue
logpolite既定値
alertassertivetrue

role="timer" と role="marquee" は暗黙的に off のため、明示的にライブ化されない限りキャッチしません。

実効値

各キャッチでは、aria-live・aria-atomic・aria-relevant の実効値を解決します。要素自身の属性、祖先からの継承（Shadow境界越えを含む）、ロールの暗黙値を踏まえ、明示値が暗黙値に優先します。明示された属性値と解決後の実効値は、各キャッチの「詳細」で対比できます。

ariaNotify()

対応ブラウザでは、document.ariaNotify() / element.ariaNotify() による命令的通知も、優先度・呼び出し対象とともにキャッチします。監視コードの注入前に行われた呼び出しはキャッチできません。

リージョンの挿入と空の通知

ライブリージョンの作られ方・更新のされ方によって、キャッチの扱いが変わります。知っておきたいパターンは3つです。

1. 内容ごと挿入されたリージョン

const status = document.createElement('div');
status.setAttribute('role', 'status');
status.textContent = '保存しました'; // 中身が入った状態で…
document.body.append(status);       // …DOMへ追加される

リージョンの挿入自体は「リージョン内の変化」ではないため、支援技術が通知するかどうかは環境によって異なります。ローディング表示を再レンダリングするフレームワークでは、このパターンが連発することがあります。注意情報付きでキャッチします。

2. 空で挿入し、後から更新 — 推奨される作法

<div role="status" id="save-status"></div>

// 通知したいタイミングで:
document.getElementById('save-status').textContent = '保存しました';

空のライブリージョンを先に用意しておき、通知したいタイミングで内容を入れる作法です。空のままの挿入はキャッチせず、内容が入った更新を通常どおりキャッチします。

3. 空の通知

document.getElementById('save-status').textContent = '';

更新は起きたのに、通知可能な内容が空だったケースです。メッセージのクリア時や、変更後の内容がすべてアクセシビリティツリーから隠されている場合などに起こります。「空」として記録します。

aria-live="off"が暗黙のライブリージョンロールと競合しています。

通知元の言語を判定できませんでした。
通知元とその祖先に lang 属性が見つかりませんでした。
ariaNotify()の呼び出しが例外を投げました。

モーダルダイアログとの関係

表示中の aria-modal="true" なダイアログ（role="dialog" / role="alertdialog"）がある間、その外側のライブリージョンを通知するかどうかは、ブラウザとスクリーンリーダーの組み合わせによって異なります。本拡張は「本拡張が判定したモーダル」（ヒューリスティック）に対する内外を各キャッチに記録し、モーダル外の通知を「キャッチ／除外／注記付きキャッチ」から選べるようにしています。

キャッチできないもの

  • ページ読み込みの監視開始前に起きた変更や、監視コードの注入前に呼ばれた ariaNotify()
  • Closed Shadow DOM内の変更
  • ライブリージョン内にあるinput要素の入力値の変化——JSによる value プロパティへの代入やユーザーのタイピングはDOMの変更として現れないため、観測できません（setAttribute() による value 属性の変更はキャッチできます）
  • スクリーンリーダーの発話内容そのもの（スクリーンリーダーごとの方言は本拡張には分かりません。本拡張はスクリーンリーダーへ渡る前のライブリージョンの値を捉えています）
